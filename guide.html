1What the program does

You type an arithmetic instruction in ordinary English. The program works it out and replies in ordinary English. Here is a real session (the answers are what Gemini actually wrote):

$ .venv/bin/python main.py
What would you like to calculate? (type quit or exit to stop) add 2 to 5 then divide the result by 3.5
[create_agent] I added 2 to 5 to get 7, and then divided that result by 3.5. The final result is 2.
[hand-written loop] First, I added 2 to 5 to get 7, and then I divided that result by 3.5 to arrive at the final answer of 2.

What would you like to calculate? (type quit or exit to stop) quit

Two things are worth noticing straight away:

  • Two answers come back. The program contains two versions of the same agent, one built for us by a library called LangChain and one written out by hand, and it runs both on every instruction so you can compare them. Most of this guide is about how they work and how they differ.
  • The AI never does the arithmetic. The AI model, Google's Gemini, reads your sentence and decides the steps: "first add 2 and 5, then divide by 3.5". Ordinary Python code does each calculation. Language models are good at understanding sentences and unreliable at arithmetic, so each does what it's good at.

3Ideas you need first

A language model is a text predictor you talk to over the internet

Gemini is a large language model (LLM). You send it text; it sends back the text it judges most likely to come next. Trained on enormous amounts of writing, that's enough for it to follow instructions, answer questions and write explanations. It runs on Google's computers: our program sends it a request over the internet and waits for the reply, usually a few seconds.

Two properties matter here. It doesn't remember anything between requests: every request must contain the whole conversation so far. And it's not a calculator: it predicts plausible text, so "7 ÷ 3.5" usually comes back as "2", but nothing guarantees it.

A system prompt is the standing instructions

Each request can start with instructions the user doesn't see: the system prompt. Ours says, in effect, "you're a calculator; do every step with a tool; never calculate yourself; explain the result in a sentence or two".

A tool is a function the model may ask you to run

Along with the conversation, a request can include a list of tools: each one a name, a description and the inputs it takes. For example: "divide: divide a by b; inputs a and b, both numbers". The model can then reply not with text but with a request: "please run divide with a = 7 and b = 3.5".

The model never runs anything itself. It only asks. Our program runs the function, then sends the result back in the next request. This back-and-forth is called function calling or tool calling.

An agent is a program that runs this loop until the job is done

"Ask the model, run what it asks for, send the results back, ask again" is the whole idea of an AI agent. The model plays the part of the decision-maker; the program does the actual work and keeps the conversation going. The loop stops when the model replies with an answer instead of a tool request.

The ReAct loop: reason, act, observe, repeat

This pattern has a name. In 2022 a research paper called "ReAct: Synergizing Reasoning and Acting in Language Models" (Yao and colleagues) showed that models solve multi-step problems much better when they alternate between reasoning about what to do next and acting (using a tool), then look at what the action produced before reasoning again. "ReAct" is short for Reason + Act.

Then and now: how the model "asks" for a tool

In 2022, models had no built-in way to request a tool, so the model was told to write its reasoning and actions as plain text in a fixed format, and the program picked the text apart. Today, models like Gemini support tool requests directly: they arrive as structured data, not prose. This program uses the modern kind.

2022: text-based ReAct

The model writes a script

Thought: I need to add 2 and 5.
Action: add
Action Input: 2, 5
Observation: 7
Thought: Now divide 7 by 3.5.
...

The program has to find "Action:" in the text and guess where the inputs start and stop. A stray word breaks it, and tools with several inputs are awkward.

Today: native tool calling

The model sends a request

{"name": "add",
 "args": {"a": 2, "b": 5},
 "id": "call_1654457..."}

The name and inputs arrive as data, checked against the tool's description. The "reasoning" still happens, inside the model, before it decides on the request. This is what both versions of our agent use.

The conversation is a list of messages

Because Gemini remembers nothing, the agent keeps the conversation as a list and sends the whole list each time. Every entry is a message with a role. These are the four kinds, as the LangChain library names them:

SystemMessage
The standing instructions (the system prompt).
HumanMessage
What you typed.
AIMessage
Gemini's reply: either tool requests (tool_calls) or the final text.
ToolMessage
A tool's result, labelled with the id of the request it answers, so Gemini can match them up.

LangChain is a toolkit for building this

LangChain is an open-source Python library for programs that use language models. It gives you ready-made pieces: a uniform way to talk to many different models (Gemini, Claude, GPT and others), message classes, a way to turn ordinary Python functions into tools, and a ready-made agent loop called create_agent. Its sister library LangGraph is what that agent loop is built on. Chapter 8 lists exactly what you get.

4main.py: where it starts

When you run python main.py, Python runs this file from the top. Most of it only defines things; the last two lines actually start the program:

main.pylines 68–69
if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))

__name__ == "__main__" is true only when this file is the one you ran (not when another file imports it). sys.argv is the list of words typed on the command line, so sys.argv[1:] is everything after main.py. There are no options, so it should be empty: instructions are typed when the program asks. Whatever number main returns becomes the program's exit status: 0 means "fine".

main(): asking, over and over

main.pylines 39–65
def main(args):
    """args is the list of words typed after `python main.py`. There are no options, so it should be
    empty: instructions are typed when the program asks for them."""

    # 1. Nothing should follow main.py.
    if len(args) > 0:
        print(f"error: didn't understand {' '.join(args)!r}. Run main.py on its own and type your\n"
              "instruction when asked.", file=sys.stderr)
        return 1

    # 2. Keep asking until the user stops.
    while True:
        # 2a. Ask. Ctrl-D or Ctrl-C stops, and so does running out of input.
        try:
            instruction = input(PROMPT).strip()
        except (EOFError, KeyboardInterrupt):
            print()
            return 0

        # 2b. quit or exit (in any capitals) stops.
        if instruction.lower() in STOP_WORDS:
            return 0

        # 2c. Calculate. A blank line just asks again.
        if instruction:
            calculate(instruction)
            print()
  • Step 1: if anything was typed after main.py, it says so and stops, explaining that instructions are typed when asked.
  • Step 2 loops forever (while True), asking with input(PROMPT). The prompt text is "What would you like to calculate? (type quit or exit to stop) ".
  • .strip() removes spaces at the ends. .lower() means QUIT and Exit stop it too, because STOP_WORDS is {"quit", "exit"}.
  • Ctrl-D ("end of input") and Ctrl-C ("interrupt") would normally crash with an error; catching EOFError and KeyboardInterrupt turns them into a quiet exit.
  • Feeding it text instead of typing: input() reads standard input, which is normally the keyboard, but the shell can connect it to text instead: python main.py <<< 'multiply 3 by 4'. When the text runs out, that's "end of input" too, so the program stops as if you'd typed quit. (This only works from your own shell: a cloud task has no input attached.)
  • An empty line fails the if instruction: test (an empty string counts as false), so it just asks again.

calculate(): run both versions

main.pylines 28–36
def calculate(instruction):
    """Run the instruction through both versions and print what each returns."""
    # 1. The version built by create_agent.
    answer, error = run(instruction)
    print("[create_agent]", answer or f"error: {error}")

    # 2. The hand-written version.
    answer, error = run2(instruction)
    print("[hand-written loop]", answer or f"error: {error}")

Both run and run2 come from agent.py and follow the same rule: they return a pair, (answer, None) if they succeeded or (None, error) if they failed. They never crash. answer, error = run(...) unpacks the pair into two variables.

answer or f"error: {error}" means "the answer if there is one, otherwise the word error and the reason". That's all main.py does. The interesting part is inside run and run2.

5agent.py: the two agents

agent.py holds both versions of the agent, and two things they share.

The system prompt

agent.pylines 17–21
SYSTEM_PROMPT = """You are a calculator. Work through the user's instruction one step at a time, in the order given.
Do every calculation with a tool (add, subtract, multiply, divide), one operation per call, and never
calculate anything yourself. Use each result in the next step, exactly as the tool returned it.
When you're done, answer in one or two plain English sentences: what you did, step by step, and the
final result. If a tool returns an error, stop and explain the error instead."""

Every sentence has a job:

  • "one step at a time, in the order given": "add 2 to 5 then divide" must not become "divide, then add".
  • "never calculate anything yourself": the whole point of the tools.
  • "exactly as the tool returned it": so Gemini passes on "2", not its own rounding of it.
  • "If a tool returns an error, stop and explain": so dividing by zero produces an explanation, not a guess.
These are requests, not rules. Nothing in the code forces Gemini to obey the system prompt. In practice it does, and the log (chapter 11) shows every tool call, so you can check that it really used the tools.

The list of tools

agent.pyline 23
TOOLS = [add, subtract, multiply, divide]

The four tools from tools.py (chapter 9). Both versions offer Gemini exactly this list.

6run(): the agent LangChain builds

The first version takes one line to build:

agent.pyline 32
agent = create_agent(llm, tools=TOOLS, system_prompt=SYSTEM_PROMPT)

You give create_agent a model (llm, Gemini, set up in config.py), the tools and the system prompt. It gives back a finished agent, with the whole ReAct loop inside it.

What create_agent actually builds

Under the surface it builds a small graph with LangGraph: boxes ("nodes") that do work, joined by arrows ("edges") that say what happens next. This is the real graph from our agent:

The graph carries a state from node to node: for this agent, just the list of messages. The model node adds Gemini's reply to it; the tools node adds the tool results.

run(), line by line

agent.pylines 35–58
def run(instruction):
    """The agent built by create_agent."""
    log.info("run: %s", instruction)
    # 1. Run the whole agent loop. It comes back when Gemini replies without asking for a tool.
    try:
        state = agent.invoke({"messages": [("user", instruction)]}, config={"recursion_limit": MAX_AGENT_STEPS})
    except GraphRecursionError:
        # 2. It went round too many times: stop.
        log.error("run: took more than %d steps; stopped", MAX_AGENT_STEPS)
        return None, "The agent took too many steps and was stopped. Try a shorter instruction."
    except Exception as exc:
        # 3. Gemini failed: down, timed out twice, key rejected, ...
        log.exception("run: Gemini failed")
        return None, gemini_failed(exc)

    # 4. The last message is Gemini's final reply, after all its tool calls.
    answer = state["messages"][-1].text.strip()
    if not answer:
        log.error("run: Gemini gave an empty answer")
        return None, "Gemini didn't give an answer."

    # 5. Done.
    log.info("run: answer: %s", answer)
    return answer, None
  1. agent.invoke(...) runs the whole loop and only returns when it reaches __end__. Its input is the starting state: a message list holding just your instruction. ("user", instruction) is LangChain's shorthand for a HumanMessage.
  2. recursion_limit is a safety stop. Every time a node runs counts as one step; past 25 steps LangGraph gives up with a GraphRecursionError. Each round (model, then tools) is two steps, so 25 allows about 12 rounds. Without it, a confused model could loop forever, spending money each time.
  3. except Exception catches everything else that can go wrong: no internet, Gemini down, key rejected, account out of credit. log.exception writes the full details to the log file.
  4. The answer is the last message. When the loop ends, the newest message is Gemini's final reply. .text gets its words; .strip() trims spaces.
Where's the system prompt? If you look inside state["messages"] after a run, the system prompt isn't there. create_agent keeps it separately and adds it to the front of every request to Gemini. In the hand-written version you'll see we have to put it in the list ourselves.

7run2(): the same loop by hand

run2 does exactly what the graph does, as an ordinary Python loop, so there's nothing hidden. First, two things it prepares once:

agent.pylines 63–64
tools_by_name = {t.name: t for t in TOOLS}
model_with_tools = llm.bind_tools(TOOLS)  # tells Gemini which tools exist and what arguments they take
  • tools_by_name is a lookup table, {"add": add, "subtract": subtract, ...}, so when Gemini asks for "divide" we can find the function.
  • bind_tools returns a version of the model that sends the four tool descriptions with every request. Without it, Gemini wouldn't know the tools exist.

The loop

agent.pylines 89–121
def run2(instruction):
    """The hand-written agent loop: ask Gemini, run the tools it asks for, repeat until it answers."""
    log.info("run2: %s", instruction)
    # 0. Start the conversation. Gemini sees all of it every time round, so it knows each result.
    messages = [SystemMessage(SYSTEM_PROMPT), HumanMessage(instruction)]

    for step in range(MAX_AGENT_STEPS):
        # 1. Ask Gemini what to do next.
        try:
            reply = model_with_tools.invoke(messages)
        except Exception as exc:  # Gemini down, timed out twice, key rejected, ...
            log.exception("run2: Gemini failed")
            return None, gemini_failed(exc)
        messages.append(reply)

        # 2. No tools asked for: this reply is the final answer.
        if not reply.tool_calls:
            answer = reply.text.strip()
            if not answer:
                log.error("run2: Gemini gave an empty answer")
                return None, "Gemini didn't give an answer."
            log.info("run2: answer after %d steps: %s", step + 1, answer)
            return answer, None

        # 3. Run each tool Gemini asked for, and add its result to the conversation.
        for call in reply.tool_calls:
            result = run_tool(call)
            messages.append(ToolMessage(content=result, tool_call_id=call["id"]))
        # 4. Back to the top: Gemini sees the tool results and decides the next step.

    # 5. It went round too many times: stop.
    log.error("run2: took more than %d steps; stopped", MAX_AGENT_STEPS)
    return None, "The agent took too many steps and was stopped. Try a shorter instruction."

Match it against the ReAct picture in chapter 3:

  1. Start the conversation with the system prompt and your instruction, both as messages.
  2. Think: model_with_tools.invoke(messages) sends the whole list to Gemini and returns its reply, an AIMessage, which is added to the list.
  3. Finished? If reply.tool_calls is empty, Gemini has answered in words, and that's the result.
  4. Act and observe: otherwise, for each tool request, run_tool runs the tool, and the result goes into the list as a ToolMessage, tagged with the request's id.
  5. Repeat: the for loop goes round again, and Gemini now sees the results.
  6. Safety stop: range(MAX_AGENT_STEPS) allows at most 25 trips round. Note this counts requests to Gemini, whereas run's limit counts graph steps, so run2 allows more rounds before giving up.

run_tool(): running one request safely

agent.pylines 67–86
def run_tool(call):
    """Run one tool Gemini asked for, and return its result as text (an error message if it can't)."""
    # 1. Find the tool Gemini asked for.
    tool = tools_by_name.get(call["name"])
    if tool is None:
        log.error("run2: Gemini asked for a tool that doesn't exist: %s", call["name"])
        return f"Error: there is no tool called {call['name']}."

    # 2. Run it with the arguments Gemini sent.
    try:
        return tool.invoke(call["args"])
    except ValidationError as exc:
        # 3. Bad arguments, eg. a word instead of a number: say what's wrong, so Gemini can fix it.
        problems = "; ".join(f"{'.'.join(map(str, e['loc']))}: {e['msg']}" for e in exc.errors())
        log.error("run2: %s%s: bad arguments: %s", call["name"], call["args"], problems)
        return f"Error: {call['name']} got bad arguments ({problems}). Fix them and try again."
    except Exception as exc:
        # 4. Anything else went wrong inside the tool.
        log.error("run2: %s%s failed: %s", call["name"], call["args"], exc)
        return f"Error: {call['name']} failed ({type(exc).__name__}: {exc})."

A tool request is a small dictionary, for example {"name": "divide", "args": {"a": 7, "b": 3.5}, "id": "call_…"}. Three things can go wrong, and each is turned into a message Gemini can read instead of a crash:

  • No such tool, for instance if Gemini invents power.
  • Bad inputs, such as a = "two". The tool checks its inputs before running (via a library called pydantic) and raises a ValidationError, which we turn into one line per problem, so Gemini can correct itself and try again.
  • Anything else that goes wrong inside the tool.

This is the main thing create_agent was doing for us silently, as the next chapter explains.

8What LangChain adds

It's tempting to think run2 uses no LangChain at all. It actually uses quite a lot: only the loop is hand-written. Here are the layers:

What both versions get from LangChain

  • ChatGoogleGenerativeAI turns the message list into Google's request format, sends it, waits, applies the timeout and retry settings, and turns Gemini's reply back into an AIMessage with tidy tool_calls.
  • @tool turns a plain Python function into a tool description, from its name, its docstring and its type hints (chapter 9 shows the result).
  • bind_tools attaches those descriptions to every request.
  • Message classes give every entry in the conversation a clear role.
  • Portability: swap ChatGoogleGenerativeAI for another model's class and the rest of the code is unchanged.

What only create_agent gives you

So which should you use? For this calculator, either. Its tools never crash and its answer is plain text, so it needs none of the extras, and the hand-written loop lets you see every step. As soon as you want structured answers, streaming, memory or approvals, create_agent saves you a lot of code. The two produce the same results, as the side-by-side output shows.

9tools.py: the arithmetic

Each tool is a short Python function with the @tool decorator on top:

tools.pylines 56–69
@tool
def divide(a: float, b: float) -> str:
    """Divide a by b: a / b. Returns an error if b is zero."""
    # 1. Calculate with exact decimals, and write the result as text.
    try:
        result = as_text(as_decimal(a) / as_decimal(b))
    except (DivisionByZero, InvalidOperation):  # InvalidOperation: 0 / 0
        # 2. Dividing by zero: return an error message for Gemini instead of crashing.
        log.error("divide %s / %s: can't divide by zero", a, b)
        return "Error: can't divide by zero."

    # 3. Log it and hand it back to Gemini.
    log.info("divide %s / %s = %s", a, b, result)
    return result

What Gemini sees

@tool reads the function and builds a description of it. This is exactly what is sent to Gemini for divide, generated from the code above:

Why exact decimals

Computers normally store numbers like 0.1 in binary, which can't represent them exactly, so simple sums come out slightly wrong. Python's Decimal type works in base ten, the way we write numbers:

ordinary numbers (float) 
0.1 + 0.2
→ 0.30000000000000004
Decimal, as the tools use 
Decimal("0.1") + Decimal("0.2")
→ 0.3
tools.pylines 13–23
def as_decimal(number):
    """The number as an exact decimal: 3.5 stays 3.5."""
    return Decimal(str(number))


def as_text(number):
    """A decimal written plainly: 2 not 2.0, 2.5 not 2.50, 1000000 not 1E+6."""
    # 1. Drop trailing zeros, and write it out in full rather than as 1E+6.
    text = format(number.normalize(), "f")
    # 2. Show "negative zero" (eg. from -0.0 * 5) as plain 0.
    return "0" if text == "-0" else text
  • as_decimal goes through str(number) first, because converting the float directly would copy its binary inexactness into the decimal.
  • as_text writes the result the way a person would: normalize() removes trailing zeros, and "f" avoids scientific notation like 1E+6. The -0 check handles a quirk: multiplying −0.0 by 5 gives "negative zero".
  • Tools return text, never crash. Dividing by zero returns "Error: can't divide by zero." as an ordinary result, which Gemini then explains, as its instructions say.

10config.py: setup

The first time any file does from config import ..., Python runs config.py once, top to bottom. It does four things.

1. The log file

config.pylines 13–21
# 1. The log file: every log.info / log.error line goes to logs/calculator_agent.log.
LOG_FILE = PROJECT_DIR / "logs" / "calculator_agent.log"
log = logging.getLogger("calculator_agent")
if not log.handlers:  # don't add a second handler if a notebook re-imports this
    LOG_FILE.parent.mkdir(exist_ok=True)
    handler = RotatingFileHandler(LOG_FILE, maxBytes=1_000_000, backupCount=3, encoding="utf-8")
    handler.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(module)s: %(message)s"))
    log.addHandler(handler)
    log.setLevel(logging.INFO)

Every log.info(...) and log.error(...) in the program writes a timestamped line to logs/calculator_agent.log. "Rotating" means that when the file reaches 1 MB it's renamed and a new one started, keeping the last three, so it never grows without limit.

2. The key

config.pylines 23–28
# 2. The key, from .env (git-ignored) or the environment. Stop at once if there isn't one.
load_dotenv(PROJECT_DIR / ".env")
GOOGLE_API_KEY = os.environ.get("GOOGLE_API_KEY") or os.environ.get("GEMINI_API_KEY")
if not GOOGLE_API_KEY:
    log.error("Missing key: GOOGLE_API_KEY")
    sys.exit("error: GOOGLE_API_KEY not set. Put it in .env (see .env.example).")

The API key is the password Google uses to know who's asking and whom to bill. It lives in a file called .env next to the code, which .gitignore keeps out of version control, so it's never published by accident. load_dotenv reads that file into the environment. If there's no key, the program stops at once with a clear message, rather than failing confusingly later.

3. The model and the step limit

config.pylines 30–32
# 3. Which Gemini model, and how many steps an agent may take.
GEMINI_MODEL = os.environ.get("GEMINI_MODEL") or "gemini-flash-latest"
MAX_AGENT_STEPS = 25  # stops a run that loops

gemini-flash-latest is a name Google keeps pointing at its current fast model. You can choose another by setting GEMINI_MODEL in .env.

4. The connection to Gemini

config.pylines 34–37
# 4. The connection to Gemini, shared by both agents: 60-second timeout; one retry on timeouts,
#    rate limits and server errors.
llm = ChatGoogleGenerativeAI(model=GEMINI_MODEL, temperature=0, google_api_key=GOOGLE_API_KEY,
                             timeout=60, max_retries=2)
  • temperature=0 makes Gemini's choices as consistent as possible. Higher values make it more varied, which suits stories, not sums.
  • timeout=60: give up on a request after 60 seconds instead of waiting forever.
  • max_retries=2 means two attempts in total, the first plus one retry. That's how this library counts. It only retries failures that might succeed next time (a timeout, "too many requests", a server error), never a rejected key.

This one llm object is shared by both versions of the agent.

INFO tools: add 2.0 + 5.0 = 7
INFO tools: divide 7.0 / 3.5 = 2
INFO agent: run2: answer after 3 steps: First, I added 2 to 5 to get 7, and then I divided that result by 3.5 to arrive at the final answer of 2.

"After 3 steps" means three requests to Gemini: two that asked for tools, and one that answered. Each took a few seconds, which is why a calculation takes several seconds even though the arithmetic is instant.

12Running it yourself

  1. Get a Gemini API key at Google AI Studio: sign in, click Create API key, and copy it. Keep it private.
  2. Create the environment and install the libraries, from inside the calculatoragent folder: 
    python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
    A virtual environment (.venv) is a private copy of Python for this project, so its libraries don't clash with other projects'.
  3. Add the key: cp .env.example .env, then put your key after GOOGLE_API_KEY= in .env.
  4. Run it: .venv/bin/python main.py, and type quit when you're done. Or feed it an instruction without typing: .venv/bin/python main.py <<< 'multiply 3 by 4'.
Each calculation costs a little. Every round is a request to Gemini, and each instruction runs through both versions, so "add then divide" makes six requests. Gemini's free tier has limits; see Google's pricing page for current figures.

13Glossary

Agent
A program that lets a language model decide which actions to take, carries them out, and repeats until the job is done.
API key
A secret string that identifies you to a service like Gemini, for permission and billing.
bind_tools
LangChain method that attaches tool descriptions to every request sent to a model.
create_agent
LangChain's ready-made agent: builds the ReAct loop as a LangGraph graph.
Decimal
Python's exact base-ten number type, used so that 0.1 + 0.2 is exactly 0.3.
Function calling / tool calling
A model replying with a structured request to run a named tool with given inputs, instead of with text.
Gemini
Google's family of language models; this program uses gemini-flash-latest.
Graph, node, edge
LangGraph's way of describing a process: nodes do work, edges say which node comes next.
LangChain
Open-source Python library of building blocks for programs that use language models.
LangGraph
LangChain's companion library for building step-by-step processes as graphs; create_agent is built on it.
Language model (LLM)
A program trained on huge amounts of text that continues a conversation; good with language, unreliable at arithmetic.
Message
One entry in the conversation: SystemMessage, HumanMessage, AIMessage or ToolMessage.
Middleware
Plug-ins for create_agent that wrap each step, for example to cap spending or summarise long conversations.
ReAct
"Reason + Act": the pattern of thinking, using a tool, looking at the result, and repeating.
Recursion limit
The maximum number of graph steps create_agent will take before stopping.
State
The data a LangGraph graph passes from node to node; here, the list of messages.
System prompt
Standing instructions sent at the start of every request, unseen by the user.
Temperature
How varied a model's replies are; 0 means as consistent as possible.
Tool
A function the model may ask the program to run, described by its name, inputs and docstring.
Virtual environment (.venv)
A private copy of Python and its libraries for one project.
